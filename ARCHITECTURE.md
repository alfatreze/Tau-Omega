# Architecture

## Recommendation: Tauri 2 + a Rust core + a TypeScript UI
**Why Tauri:** one small native installer per OS (about 5-10 MB against 100+ MB for Electron), a Rust backend that is fast at the two heavy jobs
here (walking and hashing tens of thousands of files, decoding covers) and memory-safe for code that writes to removable media, and a normal
web UI so screens are quick to build and test. Access to raw volumes and the file system is straightforward through Rust; the front end never touches the disk.
It signs and notarises like any native app (macOS Developer ID + notarytool; Windows Authenticode / Trusted Signing).

**Alternatives considered and why not:**
* *Electron:* fine, but heavy, and the disk-heavy logic would still want a native module. Choose it only if the team is JS-only and installer size does not matter.
* *Python + PySide6 (reusing `tau_library.py` directly):* fastest start, but packaging, notarisation and auto-update on both OSes are the painful part, and startup and size are poor.
  It stays useful as the **reference oracle** for conformance tests, not as the product.
* *Native per OS (SwiftUI + WinUI):* best fit, two codebases; not worth it for one developer.
* *Flutter / Qt:* viable; Qt is heavier and Flutter's desktop file/volume story is weaker. Neither beats Tauri here.
**Fallback plan:** the Rust core is a library crate with a CLI, so if the shell ever changes (Tauri to something else) nothing of value is lost.

## Layout (Cargo workspace + UI)
```
tau-omega/
  crates/
    tau-core/        pure library: no UI, no async runtime requirement beyond tokio for IO
      card/          volume detection, card model (cores, platforms, assets, settings, screenshots), free space, eject
      cores/         parse core.json/data.json/interact.json, capability detection (library support), registry of known cores
      scan/          media scanner: walkdir, file kinds, junk filters, incremental cache
      tags/          ID3v2.3/2.4, ID3v1, FLAC Vorbis; duration; cover extraction (no full-file reads)
      names/         ASCII normalisation (NFKD), path limits, collision handling, FAT rules
      index/         writer, reader/verifier (the firmware loader logic), sort keys, letters, playlists, E-codes
      art/           cover extract/optimise/scale (phase 5), thumbnail cache; art-file writer when the format is enabled
      sync/          plan builder, executor, verify, manifest, dry-run, journal/undo, progress events
      cores_ops/     install/remove/update cores from zip or folder, rbf reversal, package checks, cache cleanup
      diag/          persisted settings and diagnostic record decoders, screenshots, logs
      testkit/       fake cards, fixture generators, golden-file helpers
    tau-cli/         binary `tau`: scan | plan | sync | verify | cores | copy | move | install | report ... (same engine as the app)
  src-tauri/         Tauri app: commands, events, permission scopes, updater (opt-in), menus
  ui/                TypeScript + Svelte (or React); state in stores; no business logic
  testdata/          golden files generated by the Python reference (checked in, with the generator script)
  docs/              copy of this folder's documents
```

## Suggested crates (verify licences and maintenance)
`lofty` (tags and properties) with a small hand-written ID3/FLAC reader for the fields that must match the reference exactly;
`walkdir`, `ignore`; `sha2`, `crc32fast`; `unicode-normalization`; `serde`, `serde_json`; `zip`; `image` + `fast_image_resize` (thumbnails);
`rusqlite` (scan cache, journal) ; `tokio`; `tracing`; `thiserror`; `notify` (card and folder watch); `sysinfo` plus small OS shims for volumes
(macOS `diskutil`/DiskArbitration, Windows `GetLogicalDrives`/volume labels, Linux `/proc/mounts`); `trash` (safe delete); `tempfile`, `insta`/`similar-asserts` (tests).
Prefer hand-written code for the index writer and reader: they must be byte-exact with the Python reference, and they are short.

## Concurrency and safety model
* One **job runner**: a job is scan, plan, sync, verify, copy, move, install. Jobs are cancellable, emit progress events (files, bytes, current path), and write a journal.
* **Plan then execute:** planning is pure (no writes) and returns a serialisable plan; executing takes a plan id and a user confirmation token.
  The UI cannot execute without a fresh plan; the CLI needs `--yes` and defaults to dry-run.
* The executor writes in a fixed order: media files, playlists, **index last** (temp file, re-parse with the reference loader logic, rename); then `sync`.
  Any error before the index step leaves the previous index intact. The journal records every created and replaced path so an undo is possible.
* Card writes are serialised per volume; two jobs never write the same volume at once.
* Long paths on Windows: use `\\?\` paths internally; Tau limits paths to 200 bytes anyway.

## Cross-platform notes
* **macOS:** volumes under `/Volumes`; NFD file names (normalise before comparing with playlist lines); remove `._*` after writes; eject via `diskutil eject`; sandbox off or use user-selected folders and a Full-Disk-Access hint for removable volumes.
* **Windows:** drive letters; case-insensitive; reserved names (CON, NUL); eject via the safe-removal API or advise the user; long path prefix; SmartScreen needs a signed installer.
* **Linux (bonus):** `/media/<user>/<label>`; AppImage or deb; not a launch target but the core must build and test there (CI runs it).
* Card identification: a volume is a Pocket card if it has `Cores/` and `Assets/` (and usually `Platforms/`, `System/`); remember cards by volume UUID/label.

## UI stack
Svelte + TypeScript + Vite, a small design system matching the Tau look (dark panel, accent colour selectable from the 19 Pocket edition colours), keyboard-first.
Screens are described in `SPEC.md`. All long lists are virtualised (7,180 tracks must scroll smoothly). Internationalisation-ready strings, English first.

## Build, CI, release
GitHub Actions: `cargo fmt/clippy/test` on macOS, Windows and Linux; a conformance job that runs the Python reference and compares outputs;
UI unit tests; Tauri build matrix producing `.dmg` (universal) and `.msi`/`.exe`; signing and notarisation on tagged releases only; checksums published.
Versioning: SemVer, independent of firmware versions, with a compatibility table (Tau Omega version -> supported index format versions -> firmware versions).

## Extension points (so later phases do not need rewrites)
1. **Core registry** (`cores.d/*.json`): describes a core family (how to find media roots, which extensions, whether it reads `tau-library.tdb`, which data slots). Tau ships built in; others are data.
2. **Index writers** are versioned modules (`v1` now); a new firmware format adds `v2` beside it and the UI picks by the target core's declared support.
3. **Media processors** (pipeline steps: ascii-names, embed-cover, optimise-cover, loudness-tag (later), transcode (later)) share one interface and are listed in the plan.
4. **Exporters** (manifest JSON, HTML report, CSV of the library) are plugins on the same report model.
5. **Card adapters:** real card, a folder acting as a card (for staging and tests), and later a network share.
