# Core Marketplace and Core Updater (spec, 2026-10-14)

> **Correction 2026-10-15 (owner pointed at the library website): the design below was first written against API v1, and that was the wrong version.** The library publishes **API v3** (`api/v3/cores.json` plus `platforms.json`, 4.5 MB, 255 KB gzipped): every release of every core with its direct `download_url`, `requires_license`, the core's own `core.json` facts (`version_required`, Dock, link port, sleep), its data slots and `updaters` (licence file, previous ids, `declare_ai`). So: no GitHub API is needed to find a zip (the 60-an-hour limit, the token question and the per-core release lookup are gone), compatibility is known before any download, and older versions are listed. v3 carries no checksum, size, description or art. The site also hosts the art as plain PNGs (`/assets/images/authors/<core id>.png`, 36x36, and `/assets/images/platforms/<platform id>.png`, 521x165), which replaces the planned ranged zip reads (M3b). Download addresses are of two shapes (checked over all 6,441 releases): a GitHub release asset (725) or a zip pinned to one commit on `raw.githubusercontent.com` (5,711, the big arcade collections); the repository named in the catalog can be stale, so the address is validated by shape, not against it. The newest release is the first in each list (matches the library's own "latest" for all 332 cores that have one). A GitHub checksum is looked up best effort (one API call, only for release assets, at download time). Where this correction and the text below disagree, this correction wins; sections 1 and 3 and the M2/M3b rows are superseded by `tau_core::catalog`, `catalog_release`, `tau_net::marketplace` and the code.

Branch `marketplace` (worktree `../tau-omega-marketplace`). Browse every openFPGA core for the Analogue Pocket, install one onto a card, and keep all installed cores up to date. Reuses Omega's reviewed install path; adds a catalog, a GitHub release resolver and two pages.

## 1. Facts (verified 2026-10-14 against the live service)

- **openFPGA Library API** (MIT, read-only, static JSON on GitHub Pages): `GET https://openfpga-library.github.io/analogue-pocket/api/v1/cores.json` -> `{"data":[Core]}`; the OpenAPI file is `.../api/v1/openapi.yaml`. 333 cores, 169 KB, all GitHub-hosted, 22 `requires_license`.
- `Core`: `identifier` (`author.Name`, equals the `Cores/<id>` folder), `platform` (display), `repository {platform:"github", owner, name}`, `requires_license`, `sponsor {github[], patreon, custom[]}` or null, `updaters {license{filename}, previous[{shortname, author, platform_id}]}` or null, `release {release_date, version, platform{category,name,manufacturer,year}, assets[{platform, filename, extensions[], core_specific}]}` (release may be null).
- **The API has no download URL, no checksum, no size, no description, no icon, no changelog.** The package is the newest GitHub release of `repository`: e.g. `https://github.com/agg23/openfpga-arduboy/releases/download/0.9.0/agg23.Arduboy.0.9.0.zip`, whose layout is the card root (`Cores/<id>/...`, `Assets/<platform>/common/`, optionally `Platforms/`). Resolution needs the GitHub API (`/repos/{owner}/{name}/releases/latest`): unauthenticated limit 60 requests/hour, so resolve lazily (on open of a core, or per installed core for the updater), cache, and use conditional requests (ETag). An optional personal token is a later setting, not in v1.
- `requires_license` cores need a user-supplied licence file (`updaters.license.filename`, e.g. `beta.bin`) placed in the core's folder; it must never be downloaded or invented.
- `release.assets` describes what the core expects in `Assets/<platform>/` (extensions, core-specific): useful to tell the user where their own ROMs go.
- Reuse already in Omega: `release_check` (GitHub release parsing, SHA256SUMS verification), `package::{inspect, plan_install}`, `install_plan::plan`, `install_exec::execute` (verified backup, rollback, catalog-cache clearing, `._` sweep), `update::assess`, card scan (`card::Core`: id, version, platforms), `ureq` in `src-tauri`, the Updates bar and Packages page.

## 2. Trust model (the part that needs care)

Tau releases are ours; these are arbitrary third-party bitstreams and zips. Rules:
1. **Plan then confirm, always** (SAFETY_RULES 2-3). Nothing is written to a card without a shown plan; the existing plan/backup/rollback executor is the only writer.
2. **The catalog is a hint, the zip is the truth.** Before planning, inspect the zip: it must contain exactly the expected `Cores/<identifier>/core.json` (author.shortname id matches the catalog identifier), only paths under `Cores/`, `Assets/`, `Platforms/` (anything else, absolute paths, `..`, symlinks: refuse), a size limit (default 200 MB, entry count limit), no executables outside what the Pocket reads.
3. **Integrity:** GitHub provides a per-asset SHA-256 `digest` for newer releases; use it when present and show "checksum verified by GitHub" vs "no checksum published" (the latter is allowed but labelled, never silent). Pin: the plan id covers the downloaded bytes' hash.
4. **Provenance shown:** author, repository link, release tag and date, licence requirement, sponsor links (opens in the browser; nothing is paid or sent by Omega).
5. **No auto-install, no auto-update.** The check is automatic (when the update setting is on), the change is always the user's.
6. **Overlap protection:** an update replaces `Cores/<id>` only; the user's saves, settings, `Assets/<platform>/common` media, other cores and the licence file are untouched (backup first, then replace). A catalog core whose `Assets` folder would overwrite existing user files is refused for those files.
7. Network scope: only `openfpga-library.github.io`, `api.github.com` and the release download hosts (`github.com`, `objects.githubusercontent.com`); one User-Agent, no identifiers.

## 3. Engine (`tau_core`, new modules; network stays in `src-tauri`)

| Module | Job |
|---|---|
| `catalog` | Parse `cores.json` (tolerant: null release/sponsor/updaters, unknown fields ignored), `Catalog { cores }`, search (id, name, author, platform, category), filter (category, manufacturer, year, requires_license, installed/update), sort, group by platform. Pure; tested on a captured real `cores.json` (`testdata/openfpga/cores.json`). |
| `catalog_release` | From a GitHub release JSON choose the zip for a catalog core (the asset whose name starts with the identifier, else the only `.zip`), read the SHA-256 digest, size and notes; reuse `release_check::parse_releases` types. |
| `core_version` | Compare two openFPGA versions that are not Tau's (`0.9.0`, `v1.2`, `2024.03.1`, `0.01b`, dates): SemVer when it parses, else numeric-dotted, else release date, else "different" (never "newer" on a guess). |
| `core_update` | Installed cores (from `card::inspect_card`) matched to catalog entries by identifier, then by `updaters.previous` (old ids that this core replaces: offer the replacement and migration, never auto-remove). Verdict per core: up to date / update available / newer than catalog / not in catalog / unknown. |
| `marketplace_install` | Download -> verify (size, digest) -> `package::inspect` + the trust checks above -> `install_plan::plan` -> existing executor. Licence-required cores: install without the licence, then show the exact file name and folder to put it in. |

Host (`src-tauri`): `marketplace_cmds.rs` with `catalog_fetch` (cached in the app cache, ETag, offline falls back to the cache with its age shown), `catalog_core_release` (one core), `updater_check` (installed cores x catalog, one release lookup per core with an update candidate, rate-limit aware), `marketplace_download`, plus the existing plan/execute commands. Card write lock as everywhere.

CLI parity (the project convention): `tau catalog [--search q] [--json]`, `tau catalog-core <id>`, `tau core-updates <card> [--json]`, `tau core-install-plan <id> --card <root>`; install via the existing `package-install` after a download.

## 6. Decisions (owner, 2026-10-14)

1. **Scope:** show every catalog core. The catalog carries no compatibility data; compatibility (`core.json` `version_required`, Dock support) is only known from the zip, so it appears as a line in the install plan, not as a filter.
2. **No checksum:** allowed, with a small notice ("No checksum published for this release") in the plan and on the detail panel.
3. **GitHub token:** not in v1 (lookups are lazy and cached; 60/hour is enough). Revisit only if rate limits bite.
4. **Tau's own cores:** skipped for now; a shared approach with the existing Tau update path is a later item.
5. **Icons and shots:** bring them, and download again only when a core's release changes. Sources: the catalog has no images and no screenshots anywhere; the only art is inside each release zip (`Cores/<id>/icon.bin`, `Platforms/_images/<platform>.bin`). Plan (M3b): read just those entries from the remote zip with HTTP range requests (central directory at the end, then the two entries), decode the Pocket image format, cache by `(core id, release tag)` in the app cache, fetch lazily for visible rows and on an explicit "Download all artwork" action, never block the list on it. If a host does not support range requests, fall back to the whole zip only when the user opens that core. No third-party screenshot scraping (READMEs are untrusted, vary, and would add a second network scope).

## 7. Add a core manually (spec 2026-10-15; M7 to M11 built 2026-10-15, real-card run pending)

Owner request: add a core that is not in the openFPGA Library, from **local files** (a zip or a folder) or from a **GitHub address typed in**, and fetch the images and information from the core itself and its files. Everything else in this document (plan then confirm, vetting, backup and rollback, no auto-install) applies unchanged; this section only adds a second way in and the preview that makes an unlisted core understandable.

### 7.1 Sources accepted

| Source | What the user gives | What Omega does |
|---|---|---|
| **Zip file** | A core package zip as authors publish it (layout of the card root: `Cores/<id>/...`, optional `Assets/<platform>/...`, `Platforms/...`) | `core_package::vet_zip` with the id **read from the zip's own `core.json`** (`author.shortname`) instead of from a catalog entry. |
| **Folder** | Either a package folder (has `Cores/`) or a **bare core folder** (`core.json` at its root, e.g. an unzipped download or a build output) | Normalised into the package layout in a temporary zip in the app cache (a bare core is wrapped as `Cores/<author.shortname>/`), then the same vetting and install path as a zip: one code path, one set of rules. A raw source repository (no bitstream) is refused with the reason. |
| **GitHub address** | `https://github.com/<owner>/<repo>` (newest release), `.../releases/tag/<tag>` (that release), `.../releases/download/<tag>/<file>.zip` (that asset), or a commit-pinned `https://raw.githubusercontent.com/<owner>/<repo>/<40-hex>/<path>.zip` | Validated by exact host and path shape (no lookalike hosts, no `user@`, no ports, no `.git`/ssh forms: refused with a plain reason). A repository address lists its releases through the GitHub API (60 lookups an hour unauthenticated, ETag-cached) and picks the zip asset (the one whose name starts with the core id, else the only `.zip`; several zips: the user chooses). The zip is downloaded with a size cap, hashed locally, then treated exactly like a local zip. |

Drag and drop: a zip or folder dropped on the Marketplace page or the Cores overview opens the same sheet (the `dropTarget` helper from the Files tab). A pasted GitHub address in the sheet's address box is enough; no account, no token (an optional token stays a later setting, decision 3 of section 6).

### 7.2 What is read from the core itself (the preview)

After vetting, before any plan, a **Preview** is built purely from the package (`core_preview`, no card needed):

- **Identity:** `core.json` metadata (shortname, author, version, description, url, date_release, platform ids) and `framework` (Pocket firmware required, Dock, link port, sleep).
- **Image:** `Cores/<id>/icon.bin` decoded (the existing `icon::decode_icon_bin`); the platform banner from `Platforms/_images/<platform>.bin` when the zip carries it, otherwise the Library's platform art from the artwork cache, otherwise a placeholder (never an invented picture).
- **Where it sits:** category > manufacturer > platform, from the Library snapshot (`taxonomy::resolve`) with the zip's own `Platforms/<id>.json` for platforms the Library does not know, so the preview shows the same grouping the Cores tree will use.
- **Files it needs:** every `data.json` slot with name, accepted extensions, exact or maximum size, required or optional, core-only or shared, and where on the card each goes; the same `file_purpose` wording as the Settings tab ("Slot "BIOS": required, exactly 16 KB"). A required slot with a fixed file name that is **not inside the zip** is listed as "You supply this file" (a BIOS, a key file), with the exact folder; this is inferred from the slots, labelled as such, and never downloaded.
- **Settings it offers:** the count and names of the options in `interact.json`.
- **The author's words:** `info.txt` shown as plain text (length-capped).
- **README and pictures (GitHub source only, optional):** the repository README (first part, plain text, links not followed) and up to three images it references from GitHub's own image hosts, each size-capped, shown in the preview only and never written to the card. This is the only step that fetches more than the core, so it is a visible switch ("Also read the README and pictures from GitHub", default on for a GitHub address, one extra request each; see decision M-2).
- **Provenance:** source kind, repository owner/name, tag, asset name, size, the SHA-256 computed locally, GitHub's published digest when present (shown as verified or "no checksum published", as in section 2), and whether the core's id is **already in the Library** (then the sheet offers "Use the Library entry" so it gets updates) or already installed (then it is an update or a replacement of the same id, with the existing downgrade confirmation).

### 7.3 Trust and safety (stricter than the catalog path, because nothing vouches for it)

1. All rules of section 2 apply (paths under `Cores/`, `Assets/`, `Platforms/` only, no traversal or symlinks, size, entry count, ratio, names the card can hold, plan id covers the bytes' hash, backup first, rollback, no auto-anything).
2. The preview carries a fixed banner: **"Not in the openFPGA Library. Omega cannot tell what this bitstream does; only install cores from authors you trust."** The install button stays disabled until the user ticks "I trust this source" (one tick per core; never remembered).
3. **Id collisions:** a package whose id is a Tau core, or equals an installed core of a *different* author/source record, is refused; the same id from the same recorded source is an update. A different platform folder is never touched unless the core declares it.
4. **No hidden extras:** files outside the allowed top folders are refused, not skipped; a `Settings/`, `Saves/` or `Memories/` entry is refused (a core package must not carry user data).
5. Network scope grows by exactly the GitHub hosts needed for the chosen source: `api.github.com`, `github.com`, `objects.githubusercontent.com`, `raw.githubusercontent.com` and GitHub's image hosts for the optional README pictures; nothing else, one User-Agent, no identifiers.
6. A local folder or zip is read in place; Omega never modifies the user's source, and the temporary zip lives in the app cache and is removed after the plan.

### 7.4 Keeping a manually added core current

The card has no record of where a core came from, and we do not add files to the card for it. Omega keeps a small **source registry** in its own app-support folder (`manual_cores.json`: core id, source kind, GitHub owner/repo/tag/asset, hash, date added, card name). It is only advice: a GitHub-sourced core appears in **Cores > Updates** with the repository's newest release compared by `core_version` (the same "never newer on a guess" rule), and every update is its own reviewed plan. A zip or folder source has no update path and says so ("Added from a file; Omega cannot check for updates"). If the same id later appears in the Library the registry entry is retired in favour of the Library.

## Install review, simplified (2026-10-16, owner: "unneeded and too much, just a very simple review")

A design critique of the old "Review the update" panel found: the decision (install or not) was buried under a "Safety net" paragraph, a capacity line, a typed confirmation and a long file table; a muted brown danger button for a safe, backed-up action; and only one core at a time. The review is now **one heading** ("Install <core> on <card>" or "Install N cores on <card>"), **one line per core** (name, version, and New / Update from / Already installed / Older build), **one summary line** ("2 files, 1.9 MB · fits (329.6 GB free) · nothing on the card is replaced" or "what it replaces is backed up first"), and **one primary button** ("Install" or "Install N cores"). It starts by itself (no separate Review step). Only real problems appear above the button: a firmware and bitstream mismatch, a downgrade (one tick), a core-check error with its override (developer tools), a cautions line, and a possible reset of saved settings. Everything else (the backup facts, caches, kept files, and the file list) is behind a closed **Details**. On a Real card with developer tools on, one inline field asks for the card's name. After installing, one heading and one chip per core say what happened; the checks and the backup path are behind Details; **Undo…** puts every install back (in reverse order). **Several cores at once:** `UpdatePlanView` takes `zips`; in manual add, **Add another core** keeps the trusted core on a "Ready to install" list and the review then covers the whole list; on the Builds page each build has a tick and a bar offers **Install N builds**. Cores are installed one after another under the card write lock; if one fails it stops there, says what was installed and what was not, and the failed core is left as it was. `install-review-test.cjs` (20 checks); the other suites were updated for the new flow. Not yet: ticking several cores in the Marketplace list and Packages page (they still install one at a time).

## Multiple sources (2026-10-16, owner: "marketplace should support multiple sources")
The list is now the union of sources; each `CatalogCore` carries `source` (`openfpga-library`, `tau-alpha`) and, for a source with channels, `channel`. The Marketplace shows source chips (only when more than one source has cores), a channel chip on each card and "Listed by" in the details. A source that cannot be reached adds a note and the others still list.
- **Tau Alpha** (`tau_core::tau_source`, `tau_net::tau_source`): ONE card, "Tau", whose `options` are the installable choices built from the releases of `alfatreze/Tau-Alpha`: **Stable** = published releases (`alfatreze.TAU`, `alfatreze.TAU Diagnostics`), **Preview** = pre-releases (`alfatreze.TAU Preview`, `... Preview Diagnostics`), **Dev**; the details sheet has Channel, Build (Standard/Diagnostics) and Version dropdowns, each option with its own release history. The release list is saved for offline use. Download goes through the Tau update path (the release's `SHA256SUMS.txt` and manifest must verify), is vetted like any core, then reviewed through the same install plan (firmware pairing, settings migration).
- **Dev** is the general local path, not a download: the Dev core explains that dev builds are never published and offers **Install a local dev build...**, which opens Add a core manually (zip or folder).
- Adding a source: produce `CatalogCore`s with a new `source` id, add its label to `SOURCE_LABELS` (UI), and route `marketplace_download` for its ids. Update checks for Tau cores stay on the Tau update bar (`Status::Excluded`).
